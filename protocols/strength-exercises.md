# STRENGTH EXERCISES — MASTER

> Personal strength database: one row per exercise — where it can be trained, current working load, how to program it, and the verified Garmin Connect enum.
> **Single source of truth for strength baselines** (migrated out of `current-status.md` on 2026-06-17). Nothing else holds working loads.

## Gyms & Equipment

Three locations. The **Gym** column on each exercise says where it can be trained.

### G1 — default (self-directed)

- Barbell · dumbbells · **kettlebells (16 kg, 20 kg only)**
- Squat rack · benches: flat, incline
- **Dual adjustable pulley** — 60 kg/arm, vertical + horizontal, rope + handles. **Crossover yes; cable row no.**
- Row-erg (cardio)
- **No dip station, no pull-up bar** → no full dips, no pull-ups here.

### G2 — self-directed

- Barbell · dumbbells (**no kettlebells**)
- Squat rack · benches: flat, incline, decline
- Pec-deck + chest-press machine
- **Single-pulley system:** low pulley (cable rows) + high pulley (lat pulldown), many bar adapters. **No crossover** (single pulley).
- Dip station · pull-up bar

### PT — coach-led

- Full facility incl. leg machines (leg press, leg extension, leg/ham curl, back extension). **The coach picks the work; the DB only stores the loads you log** — it does not drive selection here.

## How this file is used

- **`/report`** owns the numbers: each week it updates **Working load × reps** and **Last logged**, and upgrades a Garmin-enum status from `⚠ guess` to `✓ <date>` (or records a new trap) when `/garmin` confirms one.
- **`/plan`** reads the **Gym** column (filter to the day's gym — default **G1**), the **Working load** (progression), and **Pattern / rotation** when programming strength. **Rotation uses a two-session lookback: rotate the selection against the last _two_ same-type sessions, not just the most recent one** (set 2026-07-29). A one-session memory degenerates into an A/B flip-flop — it produced a Jul 27 Push that repeated six of Jul 13's seven slots inside fourteen days, having "rotated" correctly off Jul 20.
- **`/garmin`** reads the **Garmin enum** column before building a strength workout — use the `✓` enum, heed the `⚠ not …` traps, and treat `free-entry` as "closest category + name in the step description." After read-back it upgrades the status here.
- **History note:** full set-by-set history lives in the daily `logbook/` files — this table holds only the _current_ working top set plus a one-line trend.

## Garmin upload: workout-level sport type

Before the per-exercise enums matter, the **workout's own sport type has to be right**, and it has its own silent-failure mode. Garmin treats the numeric `sportTypeId` as authoritative and **remaps the sport when the ID and the key disagree, without any error** — the key stays in the payload, every step uploads perfectly, and the workout simply lands under the wrong sport.

**Always send exactly this for strength:**

```json
{"sportTypeId": 5, "sportTypeKey": "strength_training", "displayOrder": 5}
```

Confirmed empirically 2026-07-30 against the Jul 29 Legs workout. Observed wrong-ID results, each of which uploaded "successfully" with all steps intact: **`sportTypeId: 13` → rucking**, **`sportTypeId: 4` → swimming**. Do not infer the ID from the commonly published Garmin tables — they do not match this account's mapping.

Verification note: `mcp__garmin__get_workout_by_id` reports `sport` as a **name only**, which is enough to detect a wrong sport but not to discover the right ID. Reading the numeric value requires the raw `/workout-service/workout/<id>` endpoint.

## Legend

- **Gym:** `G1` / `G2` / `PT`; `G1·G2` = either self-directed gym.
- **`✓ MM-DD`** — `exerciseName` survived a `get_workout_by_id` read-back on that date (year 2026).
- **`⚠ guess`** — best candidate enum, not yet confirmed; `/garmin` must verify on the next upload and date it.
- **`⚠ not X`** — known silent-drop trap: Garmin keeps the category but discards `X`; use the listed name instead.
- **`free-entry`** — no surviving `exerciseName`; upload with the category shown and put the real name in the step `description`.

> **Core pattern coverage (added 2026-08-10, athlete-raised).** The athlete flagged that core selection lacked variation, and an audit of the June–August sessions confirmed it — but the problem was structural rather than a shortage of ideas. Of the four core patterns, **two had exactly one G1-legal option each**: anti-extension was plank alone (the ab wheel has never been available there), and dynamic flexion was cable crunch alone (both hanging variants need a bar, which is G2-only). The two-session rotation rule cannot rotate a pattern with one option, so those slots either repeated or were dropped — and in practice they were dropped, which is how the 70 kg cable-crunch load-up went unattempted through two consecutive Pushes. **Five rows were added to close it:** barbell rollout and long-lever/body-saw plank (anti-extension), reverse crunch and weighted bench sit-up (dynamic flexion), Copenhagen plank (anti-lateral-flexion). Every pattern now has **at least two G1-legal options**.
>
> **Select by pattern, not by novelty.** For a 10K runner the transfer sits in **anti-rotation and anti-lateral-flexion** — resisting pelvic drop and trunk rotation at footstrike — not in flexion volume. So a core pair should take one bracing/anti-rotation slot and one dynamic slot; adding a third crunch variant is not variation that earns anything. The Copenhagen plank and the two carries are the most running-specific entries in this block and are the most under-used.
